# Internationalisation

Sorriso speaks 8 languages: `it` (default), `en`, `de`, `fr`, `es`, `pt` (pt-PT), `ro` and `pl`.
The i18n core in `src/i18n/` has no dependencies. It is typed from the English dictionary, and it
renders the same bytes on the server and in the browser.

| Role | Locale |
| --- | --- |
| Default for visitors with no preference | `it` |
| Source of dictionary keys (the type source and the runtime fallback) | `en` |
| **Authoritative for legal and consent texts** | `it` (see [Legal and consent texts](#legal-and-consent-texts)) |

  provider.tsx         I18nProvider, useT, useLocale                         ('use client')

Everything in `src/i18n` except the dictionary files is frozen (owned by the lead). Each
namespace's English file belongs to one package; the non-English files belong to the
translation package (WP9), except `it/patientMessages.ts` (WP3) and both `consents` files (lead).

| Namespace | Owner | Notes |
| --- | --- | --- |
| `common` | lead | buttons, statuses, channels, categories, roles, language names, prices, OTP texts, generic errors |
| `consents` | lead | every consent and objection text; Italian authoritative |
| `site`, `a11y`, `booking`, `manage`, `errors`, `accessibility` | WP1 | |
| `dashboard`, `calendar`, `analytics` | WP2 | |
| `patientMessages`, `reminders` | WP3 | `patientMessages` is server-only |
| `privacy`, `legalPatient`, `privacyMessages` | WP4 | `privacyMessages` is server-only |
| `privacyAdmin`, `legalPractice`, `privacyAdminEmails` | WP5 | `privacyAdminEmails` is server-only |
| `auth`, `security`, `authEmails` | WP6 | `authEmails` is server-only |
| `marketplace`, `reviews`, `catalog`, `reviewEmails` | WP7 | `reviewEmails` is server-only |
| `care`, `careMessages` | WP8 | `careMessages` is server-only |

Server-only namespaces hold SMS and email texts. `getMessages()` and `useT()` refuse them, so they
never reach a browser bundle.

## Writing dictionaries

English files are `export default { ... } as const`. Keep the `as const`: the literal types are
where keys, placeholders and plurals are typed from.

```ts
import { p } from "../../plural";

export default {
  title: "Book a visit at {clinic}",
  slotsLeft: p({ one: "{count} slot left", other: "{count} slots left" }),
  terms: "I accept the <link>terms</link>.",
} as const;
```

Other locales write `export default { ... } satisfies DeepPartial<Messages["booking"]>`. A key
English does not have, or a typo in one, fails to compile.

- **Placeholders** are `{name}`: letters, digits and `_`, no spaces and no formatting syntax.
  Format numbers, dates and money before passing them in.
- **Plurals.** Never build a sentence with `n === 1 ? ... : ...`; use `p()`. English needs
  `one` and `other`. Translations need `one`, `few`, `many` and `other` for `pl`; `one`, `few` and
  `other` for `ro`; and `one` and `other` for the rest. `many` is optional in it, fr, es and pt,
  where CLDR uses it only for millions. A missing category falls back to that locale's `other`
  (never to English). `pt` follows pt-PT rules, so 0 is plural.
- **Markup** is `<tag>...</tag>`, rendered with `rich()` (below). Translations keep the same tags.
- **SMS texts** (`patientMessages`, `careMessages`, `privacyMessages`, `common.otp`) use straight
  quotes, no `…`, and the shortest natural phrasing (GSM-7, segment budget).
- **No empty strings.** An empty value counts as missing and falls back to English.
- Never concatenate translated fragments. Give the translator the whole sentence with placeholders.

## Reading texts

Server components, actions, emails and messages:

```ts
import { getT, getRequestLocale } from "@/i18n/server";

const locale = (await params).locale;          // pages under [locale]: take it from params
const t = getT(locale, "booking");             // synchronous, memoised
t("title", { clinic: org.name });              // vars are required exactly when the key has placeholders
t("slotsLeft", { count: 3 });                  // plurals need a numeric count
```

Client components get the namespaces from the nearest `<ClientMessages>` above them:

```tsx
// layout or page (server)
<ClientMessages locale={locale} ns={["common", "booking"]}>
  <BookingFlow />
</ClientMessages>

// BookingFlow.tsx ('use client')
const t = useT("booking");
const locale = useLocale();
```

Nested `<ClientMessages>` for the same locale add their namespaces to the ones from above, so a
page loads only what its own client components need on top of the layout's set. `useT()` on a
namespace that was not provided throws in development.

**Computed keys** (a status from the database, an API error code): narrow them with `t.has()`.
Use `as const` so the key keeps its template type:

```ts
const key = `errors.${code}` as const;
return t.has(key) ? t(key) : t("errors.unexpected");
```

**Rich text:**

```tsx
import { rich } from "@/i18n/rich";
<p>{rich(t("terms"), { link: (c) => <a href={lhref(locale, "/legal/terms")}>{c}</a> })}</p>
```

`rich()` never parses HTML. Unknown tags render their content without a wrapper. A stray closing
tag stays visible as text.

**Missing keys.** A locale that lacks a key renders the English text, because `registry.ts`
merges every locale over English. A key missing even in English renders as the key itself, with a
one-time console warning in development.

## Which language?

| Surface | Order |
| --- | --- |
| Public pages `/{locale}/...` | the URL. `src/proxy.ts` redirects unprefixed paths to the `NEXT_LOCALE` cookie, then `negotiate(Accept-Language)`, then `it` |
| `getRequestLocale()` | `x-sorriso-locale` header (set by the proxy from the URL), then `NEXT_LOCALE`, then Accept-Language, then `it` |
| Dashboard: `getStaffLocale()` | `users.locale`, then `NEXT_LOCALE`, then Accept-Language, then `organizations.defaultLocale`, then `it` |
| Patient messages | `patients.locale` (chosen at booking, editable in the privacy center) |

- The `NEXT_LOCALE` cookie is set **only** when someone explicitly picks a language
  (`/api/locale`). Automatic detection never sets it.
- Nothing in the core requires the cookie. **The embed switches language by URL**
  (`/{locale}/embed/{org}`), because a cross-site iframe cannot set or read first-party cookies.
- Client components never read `navigator.language`. They call `useLocale()`.

## Dates

```ts
import { fmtDay, fmtWhen, fmtTime, fmtRelativeDay, capitalizeFirst } from "@/i18n/datefmt";

fmtDay("2026-10-13", "medium", "pl")            // "wtorek, 13 października"
fmtDay("2026-10-13", "monthYear", "pl")         // "październik 2026"
fmtWhen(appt.startsAt, org.timezone, "it")      // "martedì 13 ottobre alle 08:30"
fmtTime(appt.startsAt, org.timezone)            // "08:30" (always 24-hour)
fmtRelativeDay(day, today, "de")                // "Heute", "Morgen", "Do., 15. Okt."
capitalizeFirst(fmtDay(day, "long", "it"), "it")  // at the start of a sentence or heading
```

Styles: `long`, `medium`, `weekday`, `short`, `wd` (short weekday) and `monthYear`.

Runtime code never calls Intl's long date formats, because their output differs between Node,
browsers and ICU versions, and that breaks hydration. Names come from `calendar-names.ts`. It is
generated once from Node's `Intl.formatToParts` with `timeZone: "UTC"`
(`npm run gen:calendar`) and committed, so every change shows up in review. Word order comes from
the hand-written `date-patterns.ts`. Months have two forms: one after a day number (the Polish
genitive "października") and one on its own (the nominative "październik"). Intl is used only for
the numeric wall-clock date and time in a time zone, which is stable across runtimes and DST-safe.

## Numbers and money

```ts
formatMoney(2500, "en")     // "€25"
formatMoney(250000, "it")   // "2.500 €"
formatMoney(250000, "es")   // "2500 €"   (es, pt and pl do not group 4-digit amounts)
formatMoney(1250000, "fr")  // "12 500 €" (no-break space)
formatDecimal(4.5, "de")    // "4,5"
formatPercent(0.12, "de")   // "12 %"
```

A static separator table drives all of these. Price labels are dictionary texts:
`common.price.onRequest`, `common.price.free` and `common.price.from` (`"from {price}"`). Compute
price and duration labels on the server and pass them to client components as strings.

## Links, SEO and validation

- `lhref(locale, "/c/studio?x=1")` returns `/it/c/studio?x=1`. `/dashboard/*`, `/api/*`, absolute
  URLs and anchors pass through unchanged. `swapLocale(pathname, "de")` gives the same page in
  another language.
- `alternatesFor(path, locale)` goes in `generateMetadata`: the canonical `/{locale}{path}`, one
  hreflang alternate per locale, and `x-default` pointing at the unprefixed path.
- Zod: `schema.safeParse(input, { error: zodErrorMap(locale) })`. Never call `z.config()`: it is
  process-wide and would leak one request's language into another.

## Legal and consent texts

**Italian is authoritative.** For notices, terms, the DPA, staff instructions and every consent
text, a privacy lawyer or DPO writes and approves the Italian version first. English and the
other locales are translations of the Italian. This is the reverse of every other namespace,
where English is the source.

- The `consents` namespace holds every consent and objection text shown to patients, one entry
  per `CONSENT_PURPOSES` value: `title` (for toggles and ledgers), `label` (the statement next to
  the unticked checkbox) and `description`. `it/consents.ts` is the reference text, and
  `en/consents.ts` is its translation. Both are frozen and owned by the lead.
- Packages render these keys exactly and never write their own consent wording. The consent
  ledger stores the text key and `CONSENT_TEXT_VERSION`, and that only proves what the patient saw
  if the rendered text came from that key.
- Changing a consent text means changing the Italian first, then the translations, and bumping
  `CONSENT_TEXT_VERSION` for that purpose (`src/lib/privacy/versions.ts`).
- Legal pages in a non-Italian locale show a banner saying that the Italian version prevails.
  The legal namespaces carry "Translation: in case of discrepancy the Italian version prevails".
- All legal and consent texts in the repository are drafts until a DPO or lawyer has reviewed
  them. WP9's glossary files list the strings still waiting for review.

## Checks and tools

| Command | What it does |
| --- | --- |
| `npm test` | includes `src/i18n/*.test.ts`. Placeholder and tag parity with English, no empty strings, required plural categories, no keys English lacks. Also prints a coverage report |
| `npm run i18n:check` | the same with `I18N_STRICT=1`, which also requires every English key in every locale (WP9's acceptance gate) |
| `npm run i18n:report` | missing keys per locale and values copied verbatim from English (`--locale pl --verbose`, `--allow Word`) |
| `npm run i18n:report -- --literals <files or folders>` | hard-coded JSX text and placeholder/title/alt/aria-* attributes in .tsx files. Exits 1 if any are found |
| `npm run gen:calendar` | regenerates `calendar-names.ts` from the installed Node's ICU data. Review the diff |

## Legacy helpers

`src/lib/datefmt.ts`, the `format*` functions in `src/lib/time.ts`, and `formatPrice`,
`pluralize` and `CATEGORY_LABELS` in `src/lib/format.ts` are thin wrappers over the core. They take
a trailing optional `locale` that defaults to `"en"`, so existing callers are unchanged. New code
uses `@/i18n/datefmt`, `formatMoney` with `common.price.*`, `p()` and `t("categories.<c>")`.
`formatPrice` keeps English labels for "Price on request" and "Free" in every locale. It is
imported by client components, so it must not bundle every locale's dictionary.

## Adding a locale

1. Add it to `LOCALES` and to every `Record<Locale, ...>` in `config.ts` (the compiler lists them).
2. Add `DATE_PATTERNS` and `NUMBER_FORMATS` entries, then run `npm run gen:calendar`.
3. Create `messages/<locale>/` with all namespace files and an `index.ts`, and register it in
   `messages/index.ts`.
4. Add its required plural categories to `messages.test.ts` if CLDR gives it more than one/other.
5. For a right-to-left language (ar), set `DIR` and check layouts with logical CSS properties.
